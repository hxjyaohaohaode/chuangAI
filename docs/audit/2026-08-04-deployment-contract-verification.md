# 部署契约与能力声明复核

复核日期：2026-08-05

## 结论

当前可证实的交付边界是“教师端、单教师、本地单租户竞赛原型”。Docker Compose
默认提供无外部模型凭据的本机 DEMO：前端只发布到宿主机
`127.0.0.1:5173`，后端 3001 与 Neo4j 7474/7687 仅在容器网络 `expose`；后端以
`AUTH_MODE=demo` 和 `DEMO_MODE=true` 启动。该结论不外推为学校多教师、公网、
LIVE Docker、完全离线、国产操作系统兼容认证或法律合规结论。

## 本轮发现并修复

1. Compose 原先使用 demo 认证却未设置 `DEMO_MODE=true`，无 Key 评审机仍可能在
   启动期失败；现已把 `DEMO_MODE=${DEMO_MODE:-true}` 写入后端容器契约。
2. 安装手册原先要求访问宿主机 3001/7474，并给出固定 Neo4j 口令；这与安全
   Compose 的实际端口边界冲突。健康检查现统一经
   `http://localhost:5173/api/health`，数据库口令必须由使用者随机生成。
3. 手册原先把统信 UOS、银河麒麟、deepin 标记为“完全兼容”，但没有对应实机
   证据；现统一标记为候选目标，要求目标机冷启动与原生模块复验。
4. 原离线步骤只打包两个基础镜像，但容器启动仍执行 `corepack prepare` 和
   `pnpm install`；现明确它不是完整离线包，并列出正式离线交付所需的预构建镜像、
   多架构、校验和与无缓存断网演练门槛。
5. 教案 DEMO 原先引用不存在的“学生自学舱”；现改为教师组织的课前诊断，并
   明确样例统计必须替换为教师核验后的真实数据。
6. LIVE Docker 预检原先可能读取宿主机 `backend/.env` 的密码配置，而实际
   Compose 将容器 `AUTH_MODE` 固定为 `demo`。现已阻断这类证据错配：即便宿主机
   注入合法格式的密码摘要、长会话密钥和 Secure Cookie，`security.server-auth`
   与 `security.deployment-contract` 仍必须失败，直至另行提供并审计 LIVE 编排。
